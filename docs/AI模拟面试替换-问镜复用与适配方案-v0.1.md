# 面试蛙 AI 模拟面试替换：问镜复用与适配方案

日期：2026-10-12
状态：原简化方案已被功能对齐要求取代；当前运行的是简化版，不代表问镜功能对齐完成。

进展：已完成通信、持久化、幂等和简化文本面试闭环。新的交付边界以 [问镜功能对齐清单](AI模拟面试-问镜功能对齐清单.md) 为准；下文的“首版”和选择性参考说明仅记录原 MVP 计划，不作为最终验收标准。

## 1. 目标与参考边界

替换原 AI 模拟面试的页面及执行链路，保留一个用户入口。管理员 `/admin/ai` 仅用于模型调试。

以问镜的面试设置、画像解析、自我介绍、导演选题、动态追问、评分验证、报告、训练计划和回放为功能对齐目标，不能用简化的题库练习替代。数据库、表结构和前端组件适配面试蛙现有架构；遇到能力或体验无法等价适配时，必须说明缺口，不自行删减。

参考仓库：[liuhan-agent/Agentic_Interviewer](https://github.com/liuhan-agent/Agentic_Interviewer)，已核对版本 `0c64377b7758d3bf12ac51073d9b92246f1dc669`。本次是源码和配置核查，没有运行问镜完整服务，也未对本项目数据库恢复、向量检索做性能验收。

## 2. 技术选择：现有能力优先

| 能力 | 面试蛙方案 | 与问镜的关系及验证边界 |
| --- | --- | --- |
| 登录、权限、用户归属 | 现有 Java 后端 | 不搬入问镜独立账号、匿名认领、BYOK 体系 |
| 服务通信 | 现有 Nacos + OpenFeign → Python/FastAPI | 不升级 Java JDK，不引入 Spring AI |
| 会话、回答、评价、报告、任务记录 | 复用现有 MySQL 实例，建议 AI 独立库和账号 | MySQL 可以存储这些数据，不因上游使用 PostgreSQL 而换库 |
| 持久化流程恢复 | 优先验证 LangGraph 与 MySQL 的检查点适配 | 数据库能存状态，不等于现成 Saver 已验证可用；先做恢复验证 |
| 题库全文及后续向量检索 | 已确定复用现有 Elasticsearch，BM25 + dense_vector 两路召回，建立独立 AI 索引 | 不默认新增 Chroma、PostgreSQL/pgvector |
| 模型调用 | 已有 OpenAI 兼容接口及 deepseek-flash 配置 | 扩展结构化输出、上下文和节点预算，不整套复制模型包装 |
| 页面 | 现有 Next.js + Ant Design | 参考问镜交互，保留面试蛙样式及技术栈 |

### MySQL、PostgreSQL、pgvector 的区别

MySQL 和 PostgreSQL 都是关系数据库，面试记录、事务、状态版本和报告持久化不构成迁移 PostgreSQL 的理由。pgvector 是 PostgreSQL 的向量扩展，承担向量存储和相似度检索，与“用 MySQL 保存面试记录”是两个问题。当前 MySQL 8.0 不作为原生向量检索引擎使用，后续向量能力由 ES 承担。

问镜存在 PostgreSQL 专属 SQL/JSONB、PostgresSaver、Chroma 检索入口和其他向量模块。这意味着直接复制代码需要适配，不代表面试蛙的 MySQL 不够用。修订前“改成 MySQL 会削弱恢复机制”的表述不准确：恢复可靠性取决于事务、检查点和执行协议的正确实现。

现有 ES 7.17.4 可采用 dense_vector + script_score 路径，但不能直接套用 ES 8 的近似 kNN 方案。向量维度限制、候选量、过滤效果、召回质量和延迟需要实测；大规模检索可能需要升级 ES 或选择其他向量引擎，当前不预先承诺性能等价。

仅在以下情况下提出额外选型，并说明证据、成本和迁移影响：

- MySQL 检查点适配无法满足所需恢复语义，且自行维护成本明显过高。
- 目标向量维度或实测规模超出现有 ES 路径的能力，调整分片、过滤和索引后仍不满足需求。
- 具体功能依赖无法合理替换的外部能力。

## 3. 从问镜参考哪些能力

1. 面试设置 → 自我介绍 → 提问 → 等待回答 → 评价 → 追问或下一题 → 报告的产品流程。
2. 题目绑定版本化评分标准；评价给出回答证据、遗漏点和建议，不能让模型临时改变最低要求。
3. 追问依据回答缺口，并限制追问次数、模型调用次数和耗时。
4. 完整轮次记录与发送给模型的裁剪上下文分开保存。
5. 状态恢复、轨迹回放和评测样例，用于定位“为什么出这道题、为什么这样评价”。

选择性适配独立逻辑和提示词，不以复制全部节点为验收目标。LangGraph 是优先验证的编排工具；首批只保留必要节点，不要求与上游图拓扑一致。若适配不合适，先说明采用持久化状态机的维护成本及缺少的框架能力，再调整方案。

评价复核按需要启用，不默认每次回答都调用第二个模型。第二次模型判断不等于人工真值。强化学习、bandit 策略更新、experience_extractor、语音视频、额度运营均不进入首版，也不以“关闭策略推广”代替真正禁用学习写入。

## 4. 服务和数据归属

浏览器只调用 Java。Java 从现有登录态取得 userId，校验会话所有权，再调用 Python；不信任浏览器传入的用户身份。Python 延续内部凭证校验和请求标识。

| 数据 | 权威维护方 |
| --- | --- |
| 用户、原始题库、业务会话归属、对外操作受理记录 | Java / 现有业务 MySQL 库 |
| 执行命令、面试状态、题目及评分标准快照、回答、评价、检查点、报告 | Python / 建议独立 AI MySQL 库 |
| 检索文档及向量索引 | Python 维护独立 ES 索引，可由源数据重建 |

同一 MySQL 实例可支持以上分工，无需增加数据库服务。两个服务分别拥有自己的表，不互相直接更新内部状态。Java 通过内部接口提供经授权的题库数据，Python 不直接读取整个业务库。Java 如缓存状态或报告，须携带版本，不能反向覆盖 Python 执行状态。

Java Long ID 跨服务及前端 JSON 使用十进制字符串，存储字段使用能承接其范围的 BIGINT 或字符串；不能照搬上游 Integer。

会话建立采用稳定 sessionId、commandId 和可查询受理状态。即使共用 MySQL 实例，跨服务创建也不能假定自动拥有原子事务，需要重复查询和对账修复。

## 5. 首版功能与实现约束

### 题库与评分

现有 Question 主要是 title、content、tags、answer，真正缺少的是难度、考察维度、必答点和最低要求等结构化标准。增加面试题元数据及版本快照，不强制采用问镜的 seed 表结构。

先选一小批 Java 后端题，通过适配器导入，人工确认评分标准。模型生成标准只能作为草稿。一次面试冻结题目和标准版本；参考答案及评分标准不能通过待答题 DTO 暴露给用户。全量同步、删除传播和增量更新后续补齐。

### 模型适配

扩展现有模型调用层，支持多角色 messages、按节点设置输出和耗时预算、结构化输出校验和用量记录。真实测试模型的结构化输出能力，不假定支持特定 response_format，也不以解析失败时伪造评分兜底。

Feign 不自动重试；模型调用初期也不自动重试。若后续引入格式修复，限制次数并记录额外费用。Key 继续仅保存在私有环境配置中。

### 执行、幂等与恢复

创建、回答、结束等命令快速受理，Python 后台执行，前端经 Java 轮询；不沿用管理员单次问答的同步超时等待整个面试流程。内部接口至少覆盖创建、查询、回答、跳过、结束、恢复及报告。

- 写请求使用稳定 commandId；回答命令另带 expectedVersion、questionId。相同 commandId、不同内容须拒绝；同一请求重发返回原状态或结果。
- 命令持久化区分待执行、执行中、成功和失败，关联输入、执行版本和结果；受理成功必须有持久化依据，不能仅启动内存线程。
- 单实例起步，也要处理并发请求和重启遗留命令；通过事务、版本校验和执行归属防止重复推进。多实例前补齐租约、接管与过期执行者写入防护。
- 回答和评分输入需持久化且版本一致。不能运行时用内存原文评分、重启后改用另一份清洗文本而不记录差异。
- 定义结果、会话推进和检查点的提交边界；关键写入失败必须显式报错。不能复制上游仅记录 warning 然后继续的持久化错误处理。
- 保证业务不重复推进；模型调用成功但落库前崩溃可能产生外部调用结果未知，不承诺模型费用 exactly-once。恢复策略须明确标记未知状态，不能盲目重放所有调用。
- 正式配置持久化失败不得静默降级成 MemorySaver。

### 页面替换

替换 `/mockInterview/add` 和面试房间，仍使用原“AI 模拟面试”菜单。提供设置、当前题、回答、执行进度、反馈、历史和报告；结束状态由接口字段决定，不匹配“面试结束”字符串。

首版文本交互，背景和 JD 先粘贴文本。旧记录可查看，不尝试转换成新流程检查点。受控验证完成后切换正式入口；保留版本回退路径，不自动调用旧 Ark 链路兜底。

## 6. 分步开发与验收

| 阶段 | 交付范围 | 验收条件 |
| --- | --- | --- |
| 0：适配验证 | 最小 LangGraph 等待/恢复流程和 MySQL 检查点试验，确认所选库版本与维护状况 | 重启恢复待答状态，事务失败可见，重复提交不重复推进；若失败先汇报选型问题 |
| 1：一轮完整面试 | 少量审核题、创建、出题、回答、基本评价、结束摘要，Java 桥接和替换页面的受控验证 | 真实 Java→Python→模型完成一轮；刷新恢复，用户隔离，错误可见 |
| 2：恢复加固 | 后台命令扫描、执行中断处理、版本冲突、持久化异常处理 | 在模型调用前后和数据库提交前后故障注入；报告重复调用风险和恢复结果 |
| 3：多轮与动态追问 | 结构化评分、证据、受限追问、上下文裁剪 | 好/差答案对照验收；证据可定位，主问题及追问预算有效 |
| 4：报告与正式替换 | 报告、训练建议、历史回放、旧记录查看 | 用户仅一个面试入口；数据可追溯；故障与权限验收通过后切换 |
| 5：RAG 与能力档案 | 题库增量同步、Embedding、ES 检索、跨场次薄弱点记录 | 检索质量和延迟达标；索引可重建；能力变化能追溯到原始回答 |

阶段 1 的基本持久化不能等到阶段 2 才做；阶段 2 通过故障注入验证复杂窗口。正式切换前必须完成恢复和权限验收。

## 7. RAG 和 Harness 的合理落点

首版结构化选题即可闭环，不把所有题目原文塞进提示词，也不为使用 Agentic RAG 而增加无效调用。

向量化需要单独选定并验证 Embedding 模型、维度、文本切分及版本/重建策略。目前已验证的是对话模型，不能用它或 stub 向量冒充语义检索。Python 可直接连接现有 ES，使用独立 AI 索引和访问权限，不修改原题目搜索索引来兼容新用途。

先完成基础检索，再针对“回答缺少证据、需要查题库决定追问”等明确场景引入多步检索决策，记录检索目的、过滤条件、引用来源、调用预算与停止原因。Agentic RAG 不依赖特定关系数据库。

Harness 落实为围绕面试引擎的状态管理、工具权限、预算、输出校验、执行轨迹、失败恢复和评测。固定人工审核的好/差回答样例，记录模型、提示词和评分标准版本；模型自评分不充当准确率基线。

本方案没有增加 PostgreSQL、pgvector、Chroma 或其他新中间件。新增依赖须服务于已明确的能力缺口，不以与问镜保持一致为理由。
