# AI 面试系统需求规格说明书

版本：v1.0 审核稿  
日期：2026-10-11  
所属项目：面试蛙  
状态：待产品审核，尚未据此开始开发

> 本文定义产品应实现的行为、规则与验收条件，不预先锁定数据库表结构或框架版本。标记为“建议值”的数量、时间和阈值，均待审核后确定。文末列出了需要确认的产品选择。

## 1. 产品目标与成功标准

### 1.1 产品定位

利用现有题库，提供具有岗位针对性、能够动态追问、有依据地评价回答、持续记录用户能力变化的文字 AI 面试训练系统。

产品应形成完整闭环：创建面试 → 按计划提问 → 用户回答 → 按需澄清、追问和检索 → 逐题评价 → 面试报告 → 针对性练习 → 独立复测 → 更新能力档案。

### 1.2 需要解决的问题

| 当前问题 | 目标行为 |
|---|---|
| AI 自由出题与平台题库脱节 | 主问题来自审核通过的题库，并有选题依据 |
| 固定问答缺少面试感 | 根据本轮回答调整追问及后续考察内容 |
| 只有对话，没有可解释反馈 | 用具体回答证据说明掌握、遗漏和错误 |
| 一场结束后无法指导学习 | 生成关联题目的练习和复测建议 |
| 模型故障可能中断体验 | 回答先保存，任务可恢复，状态可查询 |
| 模型评价可能波动 | 使用版本化评分标准、人工样本和持续评测 |

### 1.3 成功标准

- 用户能够完成一场面试，并回看全部有效回答、逐题反馈和整体报告。
- 每项能力判断能够追溯到题目、回答、评分标准及评价版本。
- 无法判断时明确标记待确认，不生成没有依据的能力结论。
- 已成功提交的回答在刷新、断线或 AI 任务失败后仍可恢复。
- Agentic RAG 相比基线的收益能够通过同一批评测样本衡量。

## 2. 用户角色与访问范围

| 角色 | 能力与范围 |
|---|---|
| 游客 | 浏览公开功能说明；创建和参与面试前须登录 |
| 登录用户 | 创建面试、提交回答、查看和删除自己的记录、查看自己的档案与练习 |
| 管理员 | 管理题目、知识点、评价标准、知识资料、发布版本和评测集 |
| 获授权的运维人员 | 查看任务状态、脱敏错误和调用指标；不能仅凭运维权限任意浏览用户回答 |

管理员初期可兼任内容审核员。普通管理页面默认不展示私人对话；用户反馈问题时，可由用户明确授权查看相关记录。

## 3. 产品范围与交付阶段

| 阶段 | 必需功能 | 阶段出口 |
|---|---|---|
| A：基础闭环 | 题库与标准、创建面试、固定题单、回答保存、逐题评价、历史列表、基础报告 | 完成一场可恢复、可解释的面试 |
| B：智能面试 | 有限追问、运行约束、知识检索、按需 Agentic RAG、执行轨迹 | 针对不同回答产生有效追问，检索收益通过评测 |
| C：持续训练 | 能力证据、练习推荐、独立复测、趋势展示 | 反馈能够指导下一次训练并验证改善 |
| D：体验与规模 | 流式体验、多实例、容量验证、运营指标 | 达到确认的体验和容量目标 |

鉴权、幂等、任务恢复、基础日志和评测从相关功能首次上线时具备，不延后到 D 阶段。

首批内容建议为 Java 后端岗位、文字输入。首版不包含语音、视频、表情分析、在线代码执行、简历文件解析、自动互联网搜索、招聘录用判断或多人面试。项目经历先使用手动文字填写。

## 4. 核心概念

| 概念 | 定义 |
|---|---|
| 主问题 | 从题库选出的一个完整考察单元 |
| 追问 | 归属某道主问题，围绕用户回答继续考察的问题 |
| 澄清 | 请用户解释表达或补充场景，不主动提供知识答案 |
| 提示 | 明确给予解题方向或知识信息，会影响证据权重 |
| 回答证据 | 用户原文及其所在轮次，关联某个评价要点 |
| 题目评价 | 综合主问题和所属追问后的最终评价 |
| 能力档案 | 按知识点聚合的、可重算的证据摘要 |
| 独立复测 | 未展示答案和提示的情况下，对同一知识点重新考察 |
| Harness | 约束单次 AI 执行、工具使用、预算、输出和恢复的程序机制 |
| Agentic RAG | 在知识依据不足时，自主决定查询、有限调整查询并结合证据作答的检索流程 |

## 5. 用户完整流程

1. 用户登录并选择岗位、工作年限、难度、模式和面试规模。
2. 系统检查题库覆盖和服务状态，生成计划并说明预计耗时。
3. 用户开始面试，每次展示一个当前问题。
4. 用户提交回答，系统先确认保存，再处理后续动作。
5. 系统根据回答澄清、追问或进入下一道主问题；必要时检索知识。
6. 一道主问题关闭后生成综合评价；训练模式展示即时反馈，模拟模式暂不展示。
7. 面试完成或用户提前结束后，系统生成包含已完成部分的报告。
8. 用户查看优势、待加强点及练习建议。
9. 用户完成练习和独立复测，系统新增证据并更新能力档案。

## 6. 功能需求

### FR-01 题目与评分标准管理

- 保留现有题目增删改查、AI 出题和题库关联能力。
- 为面试题维护岗位、难度、适用年限、知识点、频率等级及来源。
- 评分标准包含考察目标、适用情境、必答要点、要点权重、常见错误、可接受的替代方案和追问方向。
- 题目与评分标准支持草稿、待审核、已发布、已停用状态。
- AI 生成的题目、标准和知识材料默认不得自动进入正式面试池。
- 修改已发布内容产生新版本；已开始面试使用原快照。
- 高频标记区分人工运营判断和外部资料依据，平台出题次数不直接代表市场高频。
- 发现实质性错误时，可以停用内容、标记受影响评价，并按审核结果安排重评。

验收：未审核题目不会被选入正式面试；修改题解后，历史面试仍能还原原有依据。

### FR-02 创建面试与生成计划

- 必填：岗位、工作年限区间、难度、面试模式。
- 建议首版按主问题数量选择规模：5 道或 10 道；预计时长仅作参考，不与严格倒计时同时约束。
- 可选：重点知识点、项目经历、是否针对历史薄弱点。
- 系统根据题库覆盖、难度、高频等级和近期出题记录制定计划。
- 主问题必须来自已发布题库。首版允许动态调整剩余题目，但应记录调整原因。
- 候选题不足时展示可用数量和调整选项，不静默重复题目或伪装成已有题库题。
- 建议同一用户同一时刻仅允许一场未结束面试；可恢复或结束后新建。
- 前端不提前取得隐藏答案、完整评分标准或未来题目。

验收：计划符合筛选条件；不足时有明确提示；不会把错误岗位的题目混入计划。

### FR-03 面试室与回答提交

- 展示当前主问题序号、追问关系、当前阶段和处理状态。
- 支持文字回答、换行、代码块；提交前显示长度限制。
- 提供提交、表示不会、跳过、结束面试操作。
- 首版建议回答上限为 8,000 字符、项目经历上限为 4,000 字符，允许配置。
- 已提交回答不可覆盖修改；需要补充时新增一条补充回答并保留原文。
- 生成下一问期间禁用重复推进；不同浏览器或标签页提交冲突时提示刷新状态。
- 明确区分“已保存，处理中”“已完成”“处理失败，可重试”。
- 页面刷新或断线后恢复服务端确认的记录；未提交草稿不承诺跨设备恢复。

验收：重复提交只产生一次有效业务结果；刷新后已提交内容和当前轮次正确。

### FR-04 面试模式

| 行为 | 模拟面试 | 训练模式 |
|---|---|---|
| 逐题评分 | 结束后集中查看 | 当前主问题关闭后查看 |
| 参考答案 | 主问题进行中隐藏 | 主问题关闭后可查看 |
| 主动提示 | 默认关闭 | 用户可请求，记录已提示 |
| 语气 | 专业、自然、适当追问 | 专业、解释性更强 |
| 能力证据 | 按实际条件计入 | 展示答案后的作答只算练习 |

面试模式创建后固定，避免中途切换造成反馈与评分含义不一致。面试官不得侮辱用户或把训练表现扩大为对人格、就业前景的判断。

### FR-05 自适应提问与追问

- 根据当前回答判断是否澄清、追问、调整剩余难度或进入下一题。
- 追问可以生成新表达或场景，但必须关联主问题的考察目标与知识依据。
- 建议每道主问题最多 2 次后续提问，澄清与追问共用该预算，避免绕过限制。
- 回答扎实时可以深入场景或权衡；表达含糊时先澄清；明确不会时允许换题。
- 不重复已经得到充分回答的问题，不无限围绕一个知识点循环。
- 一场面试保持既定知识点覆盖；历史薄弱点不能完全挤占其他内容。
- 模型提出动作建议，由程序校验轮次、状态、预算与权限后执行。
- 在线分析只用于下一步决策；最终评价使用主问题及追问的完整记录。

验收：同一主问题面对不同回答能产生不同且相关的追问；次数和状态约束始终有效。

### FR-06 知识库与 Agentic RAG

- 知识库包含考试材料和经审核的参考知识，记录来源、适用技术版本、审核状态与内容版本。
- 正常题库选题采用结构化条件；RAG 用于补充评价和追问依据。
- 当前依据不足、用户提出替代方案或出现知识冲突时，可以触发检索。
- 允许在首轮证据不足时有限改写查询；建议每次决策最多 2 轮检索。
- 检索不到、内容冲突或超过预算时，追问确认或标记依据不足，不强行下结论。
- 记录使用的文档版本与证据片段，不能引用不存在的来源。
- 首版只检索内部审核资料，不自动搜索公开互联网。
- 知识材料中的文本指令不能改变工具权限或面试规则。
- 新增、修改、停用资料后，索引状态可查询；停用资料不得继续参与新的检索。
- 审核后的题目版本不因知识库更新被悄悄替换；补充检索依据独立记录。

验收：能够处理标准以外的合理回答；能回溯检索依据；找不到资料时明确保留判断。

### FR-07 回答评价

- 先对评价要点标注掌握、部分掌握、错误、待确认或未考察，再按明确规则汇总。
- 建议展示 0～100 的题目分数，并同时展示维度、证据和解释；未考察要点不能直接按错误扣分。
- 正确性、完整性、深度、应用能力、表达清晰度按题型配置权重，不使用一套权重覆盖所有题型。
- 记录用户原文片段、所属轮次、命中要点、错误、遗漏及建议。
- 区分独立答对、中性澄清后答对、提示后答对和看过答案后答对。
- 用户选择“跳过”只记未完成；明确表示不会可作为有限负面证据，不能据此否定整个知识领域。
- 不将模型自报置信度当成经过统计校准的正确概率。
- 对合理替代方案可判定正确；资料不足时允许待确认。
- 未知技术版本、题目歧义或标准问题应降低结论确定性，不直接归责用户。
- 评价失败时显示待完成或失败，不能填充伪造分数。
- 重新评价新增版本，保留原因和旧结果；同一回答不会重复累计能力证据。

验收：评价引用真实回答；评分可按规则解释；提示和未考察状态不会被混同处理。

### FR-08 面试报告与历史记录

- 历史列表支持按时间、岗位、状态筛选，展示完成规模和报告状态。
- 报告包括面试配置、完成情况、逐题表现、优势、待加强点、证据和练习入口。
- 整体评价说明已考察范围，不把局部成绩表述成用户全部能力。
- 提前结束可以生成部分报告，并明确未完成内容。
- 尚有评价任务未完成时展示“报告生成中”或“部分报告”，不能表现为全部评价已完成。
- 报告基于有效评价生成；模型总结不能新增没有证据支持的错误或优势。
- 用户可以对某项评价提交“不准确”反馈并注明原因；首版记录反馈，不承诺人工即时答复。

验收：报告结论能回到具体回答；提前结束和部分失败时内容与状态一致。

### FR-09 能力证据与成长档案

- 按知识点展示已掌握、待加强、待确认和证据不足的内容。
- 每项结论关联来源、难度、作答条件和日期。
- 单次低分不直接成为长期结论；样本不足时明确说明。
- 不同题目难度、模型或标准版本变化时，不直接把原始分数差异解释为成长。
- 基于证据规则聚合档案，能够在重评、撤销错误标准或删除记录后重算。
- 训练中已展示答案的结果不作为独立掌握证据。
- 只允许用户查看自己的个人能力档案。

验收：新增、替换和删除证据后档案正确更新，不重复计算同一题的多次评价版本。

### FR-10 练习推荐与独立复测

- 根据有效薄弱点推荐已发布题目，展示推荐原因。
- 练习可以展示讲解和答案，但与独立复测记录区分。
- 复测优先选择同知识点的不同题目或不同场景；题库不足时说明重复使用。
- 复测中隐藏答案和提示，记录距离上次练习的时间。
- 通过新证据说明改善，不保证“练过即掌握”。
- 首版使用站内练习清单，不包含邮件、短信或自动定时提醒。

验收：推荐与薄弱点一致；练习结果不会被误计为独立复测结果。

### FR-11 管理与运行观察

- 管理员可维护知识点、发布标准、查看知识索引状态和内容反馈。
- 可配置题目规模、追问预算、模型调用预算和功能开关。
- 记录模型、提示词、评分规则和知识版本，支持评测比较与版本回滚。
- 观察任务积压、失败率、调用耗时、检索次数、Token 与估算费用。
- 用户界面使用“正在分析回答”等业务表达，不暴露内部提示词、工具日志或运行组件名称。
- 执行轨迹记录动作、工具参数摘要和证据引用，不要求保存模型内部思考过程。

验收：能够按任务追踪一次失败，且普通用户无法获取内部配置和他人数据。

## 7. 状态与一致性要求

### 7.1 面试和任务状态

- 面试生命周期：待开始 → 进行中 → 已结束。结束原因区分正常完成、用户提前结束和长期未继续关闭。
- 题目轮次阶段：等待回答 → 回答已保存／处理中 → 下一问已就绪或主问题已关闭。
- 评价与报告状态独立于面试生命周期；面试结束不等于报告已完成。
- AI 任务状态：待处理、处理中、成功、可重试失败、最终失败、已取消。
- 建议离开页面后可在 24 小时内恢复；超期关闭规则需产品审核。

### 7.2 必须成立的规则

- 业务后端是面试状态、任务调度和最终记录的唯一权威。
- AI 服务管理单次执行的工具、预算与输出，不独立推进业务面试状态。
- 回答与对应任务在同一事务中保存后，才能向用户确认提交成功。
- 幂等提交和轮次校验同时存在；不同请求 ID 也不能重复推进同一待答轮次。
- 工作任务可被接管，但过期执行者不能提交结果；迟到结果不能恢复已结束面试。
- AI 生成请求可能重复执行，业务结果最多生效一次；不承诺模型调用永远只计费一次。
- 重试不能导致重复答案、重复主问题或重复能力证据。
- 长时间外部模型调用不得占用数据库事务。

## 8. 异常与降级行为

| 场景 | 用户可见行为 | 系统处理 |
|---|---|---|
| 提交响应丢失 | 可查询或再次提交 | 返回已有提交结果 |
| AI 超时 | 回答已保存，显示处理失败或重试中 | 有限重试，不推进错误轮次 |
| 评价服务不可用 | 评价待完成 | 恢复后补处理，不填假分数 |
| 动态追问不可用 | 可等待或按计划继续 | 使用已准备的题库主问题，不凭空生成评价 |
| 知识检索不足 | 需要进一步确认 | 记录缺失依据，避免确定性误判 |
| 用户结束时生成仍在进行 | 面试已结束 | 作废后续出题；已提交回答仍可评价 |
| 进程重启或任务租约到期 | 任务状态可查询 | 安全接管，拒绝过期执行结果 |
| SSE 断线 | 重连或查询最终结果 | 以持久化内容为准，不将片段当完成结果 |
| 并发额度已满 | 明确排队或稍后再试 | 有界等待，不无限占用资源 |
| 模型结构化输出不合法 | 显示处理中或失败 | 有限修复，失败结果不入正式评价 |
| 登录过期 | 提示重新登录 | 已保存内容保留，恢复前重新校验权限 |

## 9. 数据、隐私与权限

- 保存面试配置、题目快照、逐轮回答、任务状态、评价版本、证据、报告和练习记录。
- 默认不向模型发送账号、手机号、邮箱等无关身份信息；项目经历可能发送给模型，应在提交入口说明用途。
- 用户有权删除自己的面试记录；相关回答、报告、检索缓存及能力贡献进入清理或重算流程。
- 建议删除后立即从业务界面不可见，在线数据在 7 天内清理；备份按明确保留周期自然淘汰，该周期上线前必须确定。
- 删除正在进行的面试先取消任务，迟到结果不得重新创建记录。
- 日志不默认记录完整私人回答、密钥或内部鉴权信息；排查所需内容采用受控访问和脱敏。
- 用户身份及数据范围由可信服务上下文确定，不接受模型自行指定要读取的用户身份。
- 外部模型供应商的数据保留政策、用户内容保留周期和访问审计规则，在上线前确认并向用户说明。

## 10. 非功能要求与验收目标

以下为建议验收值，须结合选定模型与部署资源确认；不是当前系统已有能力。

| 项目 | 建议目标／要求 |
|---|---|
| 提交确认 | 在约定负载下，回答持久化确认 P95 ≤ 1 秒，不包含模型处理 |
| 下一问生成 | 在固定输入规模下，端到端 P95 ≤ 20 秒；超时进入明确等待／失败状态 |
| 题目综合评价 | 正常服务条件下 P95 ≤ 60 秒 |
| 报告生成 | 依赖评价完成后 P95 ≤ 60 秒 |
| 初始测试负载 | 20 场活跃面试、模型调用并发上限 5；队列上限和超时显式配置 |
| 外部调用预算 | 连接、单次生成、检索和总任务均设置上限，避免层层重试放大 |
| 故障恢复 | 模拟工作进程中断后，任务在配置的租约回收窗口内恢复；建议 ≤ 2 分钟 |
| 数据一致性 | 重复提交、任务接管、迟到返回测试中不出现重复业务生效 |
| 流式展示 | 只有完整且校验通过的动作才能影响状态；明确完成事件与片段事件 |
| 兼容性 | 原刷题、登录、题库管理保持可用；AI 路由可按版本切回 |
| 可观测性 | 一个业务请求可关联任务、模型调用、检索和最终结果 |

容量验收必须写明模型、输入长度、部署资源、并发定义和供应商限额。模型超时不能靠无限增加服务线程解决。

## 11. AI 质量评测与发布准入

在评价功能开发前建立人工标注集，建议首批至少 50 份回答，覆盖正确、部分正确、明显错误、合理替代方案、版本差异、提示后答对和诱导改变规则等情况。

每次模型、提示词、检索方式或评分标准的重大变化，使用固定保留样本评测，避免仅在调优样本上比较。

| 指标 | 建议首批准入条件 |
|---|---|
| 回答引用定位 | 所有展示的直接引文能够定位原文 |
| 要点判定一致性 | 与人工标注一致率 ≥ 85%，待确认项单独统计 |
| 明显错误被判完全正确 | ≤ 5% |
| 合理替代答案被直接判错 | ≤ 10% |
| 追问相关性 | 人工审核相关且有价值的比例 ≥ 85% |
| 流程约束 | 专项测试中无超次数、非法轮次推进或越权读取 |
| Agentic RAG | 在相同样本上改善目标错误类型，且耗时和成本在预算内 |

上述比例是建议门槛。小样本结果需报告样本数与错误案例，不解释为线上总体准确率。Agentic RAG 不达收益要求时，保留普通检索并限制自主检索范围。

## 12. 最小端到端验收用例

| 编号 | 用例 | 预期 |
|---|---|---|
| AC-01 | 用户完成 5 道题面试 | 记录、评价、报告可回看 |
| AC-02 | 同一回答连续提交两次 | 一次有效提交与一次轮次推进 |
| AC-03 | 提交成功后刷新页面 | 原文及当前状态恢复 |
| AC-04 | AI 调用失败后重试 | 回答不丢失，结果不重复 |
| AC-05 | 两个执行者先后处理同一任务 | 过期执行者不能覆盖有效结果 |
| AC-06 | 生成途中结束面试 | 不再出现新题，已答题仍可生成报告 |
| AC-07 | 用户提出参考答案以外的合理方案 | 检索或待确认，不直接按关键词判错 |
| AC-08 | 用户获得提示后答对 | 明确标记提示条件，能力证据不等同独立答对 |
| AC-09 | 用户跳过题目 | 记未完成，不直接标记整个知识点不会 |
| AC-10 | 管理员更新标准 | 历史依据不被覆盖，新面试使用新版本 |
| AC-11 | 重评同一回答 | 保留版本，能力证据不重复累计 |
| AC-12 | 删除面试记录 | 用户不可见，任务取消，能力档案重算 |
| AC-13 | 用户要求忽略评分规则或读取他人记录 | 不改变权限和流程 |
| AC-14 | 候选题不足 | 告知不足并提供调整，不静默重复 |
| AC-15 | 知识文档停用 | 后续检索排除该文档 |
| AC-16 | 流式连接中断 | 查询持久化结果恢复，不把残缺片段算完成 |

## 13. 技术约束与尚未锁定的实现选择

- 按当前方向保留 JDK 8 业务后端，新增独立 JDK 17 Spring AI 服务。
- 普通内部请求拟采用 OpenFeign／HTTP；流式交互单独设计。
- 按当前讨论采用 Nacos 服务注册发现，依赖版本须分别验证兼容性。
- MySQL 保存业务权威数据；Redis 可辅助限流和短期状态，不能成为回答唯一存储。
- 向量存储、嵌入模型、重排方案、Spring AI 具体版本、MQ 是否引入，均在技术设计阶段基于验证决定。
- 不要求建立多个相互聊天的 Agent；面试决策、评价、报告首先作为逻辑职责划分。
- 通用对话接口只作为迁移兼容入口，正式面试采用有明确输入输出的业务契约。
- 回退模型适配器不等于回退业务数据格式；新旧面试记录必须有可区分的版本和兼容读取方案。
